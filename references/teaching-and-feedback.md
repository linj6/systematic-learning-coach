# 教学与反馈规范

## 一、教学顺序

1. 将当前主题放到完整知识地图中，说明它与上下游知识的关系。
2. 说明该机制要解决的问题，并提供一个具体的业务或现实场景。
3. 沿着一条端到端流程展开，标注参与者、职责边界及关键状态。
4. 解释因果机制、设计理由、替代方案与失败条件。
5. 在充分讲解后提出**一道**有针对性的问题；复习诊断模式可以先提问。

当组件关系、执行顺序或状态变化难以理解时，优先使用架构图、时序图或时间线。解释图中每条关键连接、状态转移与异常分支。类比可以辅助理解，但不能取代准确的技术解释。

## 二、第一性原理辅助的因果教学（跨领域通用）

对概念密集、上下游依赖强或学习者只记住术语却不理解联系的主题，优先采用：

**目标/任务 → 具体问题与约束 → 基础事实与假设 → 推导所需能力 → 引入候选机制 → 最小案例或验证 → 回到整体知识地图。**

- **先提问题，再给术语**：先说明缺少某种能力会遇到什么困难，再解释某个概念如何提供该能力；不要从术语清单直接跳到公式或实现。
- **区分事实、假设、推论和设计选择**：行业常见方案不是不可违背的第一原理；从需求只能推导出所需能力，通常不能唯一推导出某种实现。说明替代路径和前提。
- **保留关键中间环节**：让学习者能解释上游输入、当前操作、下游输出，以及每一步为何必要；遇到断层先补最小前置知识，再继续主线。
- **回到全局依赖图**：每学完一个机制，说明它解决哪一个子问题、依赖哪些知识、输出供谁使用；可用简图持续连接已学概念。
- **通过反事实理解边界**：酌情问“如果没有这个机制会怎样？可否用别的机制替代？代价是什么？”，但不把反事实推演当作唯一答案。
- **以最小验证封闭因果链**：使用可手算的小例子、可观察实验、案例比较或推理检验；不适合实验的领域采用可信证据及反例，不编造实测。
- **控制深度，不无限还原**：L1 直观目的与功能、L2 输入/机制/输出与边界、L3 形式证明或底层优化。这里的 L1–L3 是*讲解深度*，不是 Skill 的 L1–L4 *掌握度评级*。通常以 L1+L2 为主，只有目标、关键疑点或证据需要时进入 L3；避免追溯所有数学公理、历史细节或底层实现。

本流程是按需触发的教学思路，不强制每个简单问题走完固定步骤，不取代先整体后局部、主动思考和掌握度评估。

**简例（LLM）**：任务是根据上下文预测后续 Token → 文本需要数值表示（Token ID 与 Embedding）→ 不同位置的信息需要交互（可选用 Attention）→ 通过 Q/K 点积形成匹配分数、Softmax 得到权重、加权汇聚 V → 回到 Transformer 中观察输入、输出与局限。不要声称 Attention 是从目标唯一推导出的必然方案，也不要把注意力权重解释为信息正确的概率。

**简例（软件工程）**：秒杀目标是有限库存下防超卖和重复购买 → 推导原子准入与幂等约束 → 对比数据库条件更新、Redis 原子操作等实现 → 用并发测试和故障窗口验证；不要一开始就把 Redis + MQ 当成业务定律。

## 三、知识点完整讲解契约（Concept Explanation Contract）

对 P0/P1 核心知识点，讲解应形成可独立理解的闭环，回答以下六类问题：

1. **是什么**：给出准确的概念、关键组成与它在整体知识地图中的位置；引入新术语时说明含义。
2. **为什么需要**：明确要解决的具体问题；说明缺少该机制时会出现什么困难或失败。
3. **如何工作**：按参与者、前置条件、执行步骤、状态变化与结果解释因果链；不跳过决定结论的中间环节。
4. **何时使用**：给出适用场景、必要前提，以及不适用或不值得使用的场景。
5. **具体案例**：至少用一个可追踪的业务或现实案例，交代初始状态、参与者、关键操作、观察结果及其原因；抽象理论优先用时间线、时序图或故障推演落地。
6. **边界与代价**：指出保证范围、失败条件、常见误区，以及引入的复杂度、资源或性能成本；只展开与当前目标相关的部分。

**强制要求**：不能仅给定义、缩写展开、术语罗列或抽象结论就宣布知识点完成。尤其不得省略“解决什么问题、什么时候使用、具体如何应用”。需要推导的结论必须补齐关键中间步骤；不确定的前提应明确说明。

**防跳跃规则**：先解释当前知识点与前置概念的关系，再引入下一个机制。遇到未解释的关键术语，先补充最小必要说明；扩展到 P2 细节时简要标记并返回主线。不要用一个新概念代替对旧概念的解释。

**完成检查**：切换到下一核心知识点前，确认讲解已覆盖问题背景、核心机制、具体使用过程和关键边界，并依据学习者回答判断是否需要补充案例或推导。**已给出定义不等于已讲清，已讲清不等于学习者已掌握**；掌握度仍依据问答和实践证据评估。

**按复杂度调节**：六个维度是讲解质量检查项，**不是强制的六段式排版模板**。简单概念可以用几句话完整交代；复杂理论应分多轮、用图和案例逐层展开。不得为了填满模板制造无关内容，也不要每次都输出重复的长篇讲义。

### 示例：BASE 不应只解释三个英文术语

不合格：只说“BASE = 基本可用、软状态、最终一致性”，随后直接切换到 CAP 或消息队列。

合格讲解路径：订单创建成功后异步发放积分 → 解释为什么跨服务难以直接依赖一个本地事务 → 订单事件可靠记录并发送 MQ → 积分消费者处理、幂等与 ACK → 消费失败重试 → 达到上限进入死信并告警、对账或人工补偿 → 说明在故障持续或补偿缺失时，不能承诺自动达到最终一致。由此再解释 BASE 的适用条件和代价。

## 三、回答批改与纠错

针对学习者的回答，依次说明：

1. **判断**：正确、部分正确、不正确或证据不足。
2. **正确部分**：指出哪些结论和推理成立，并解释原因。
3. **关键缺口**：找出最重要的错误前提、因果环节、适用条件或边界。
4. **修正推导**：完整解释正确机制，尽可能提供具体反例。
5. **必要时复验**：只有需要确认误解已经修复时，才提出一道变式题。

不能把只记住关键词当作真正理解；也不能因为学习者没有回答题目未要求的细节，就否定一个简洁但正确的答案。学习者已经能清楚解释核心机制时，应进入下一单元。若连续两次未理解，应更换讲解形式，而不是重复相同问题。

## 四、会话节奏与状态管理

在教学过程中持续跟踪：当前主题、学习目标、知识地图位置、尚未修复的误解、已有证据和暂缓主题。只在自然的阶段节点总结进度，不要每轮都输出冗长的进度报告。

当讨论偏离主线并进入 P2 细节时，可以简要回答，再回到当前目标。不要为了完成预设流程而强制每轮提问。
